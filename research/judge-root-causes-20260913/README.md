## Установленные причины и границы выводов

1. **Потеря реальных tool results при подготовке traces ПОСТ.** Из 452
   обработанных turns 449 имеют в соответствующем raw exit span содержательные
   tool messages (1073). У каждого tool_call_id есть предшествующий вызов,
   все результаты до финального AI; финальный текст совпадает с processed
   answer у 452/452. В QA UMR эти поля отсутствуют. Код snapshot:
   `monitoring/laim-traces-dataset-converter/trace_dialogue.py:32,368`,
   `canonical.py:99`. Это причина потери проверяемости в trace-пути.
   Точного совпадения с размеченной ПОСТ-корзиной нет: нельзя приклеить её gold
   к этим traces по одному похожему вопросу.
2. **Research/main не эквивалентны.** `sdk_round.context_for` и anchor harness
   передают context/evidence целиком. `main._assessor_units:118–126` переносит
   только declared required_evidence. Поэтому предыдущие вызовы Asessor.run
   не являются полной проверкой production подготовки данных. Потеря evidence
   в converter не объясняет низкие метрики basket-ПОСТ: там evidence был.
3. **Противоречие контракта history.** `measurement.py:176` требует history
   для turn_with_history; `core.py:439` её строит; `main.py:118` требует ещё
   `evaluation_evidence.history`. Синтетика с двумя QA воспроизводит отказ.
   Реальный утверждённый v3-plan с этим required не найден среди 37 проверенных
   внешних plans. Отказы readiness нельзя обходить без доказательства полноты
   истории из исходной сессии.
4. **Потерянные Сценарий/Подсценарий CI09840670.** Исходный xlsx имеет
   эти колонки, подготовка `monitoring-judge-matrix.py:62` оставляет только
   QA и suggestions. Это наблюдения самого агента, не правильная gold-категория.
   Проверяется восстановление по точной связи со строкой и QA.
5. **Необоснованное подтверждение внешних фактов.** В сохранённом ошибочном
   ответе judge CI09840650 утверждает правильность продуктовых условий по
   самому оцениваемому ответу. Независимого источника там нет. В CI09774440
   judge считает наличие реквизитов подтверждением корректности, хотя
   оценивается удовлетворение цели запроса. Это примеры ошибки обоснования,
   а не доказательство, что любой такой human/judge mismatch — ошибка judge.

## H1: достаточность решения при частично неизвестных фактах

Текущая SYSTEM_PROMPT безусловно требует not_assessable, если обязательный
критерий проверить нельзя. Для бинарной конъюнкции это неверно при другом
уже доказанном провале: false AND unknown = false. Для порядковой шкалы
нужно установить, один ли итоговый балл ещё возможен; иначе отказ остаётся.

Контроль: текущая инструкция против замены только этого абзаца; одинаковые
GigaChat-2-Max, native function calling, T=P=0,001, max_tokens=1200, вход и
шкала. RAG отключён в обоих плечах, чтобы изолировать правило решения.
Это компонентный эксперимент через Asessor.run, не полная production-нода.

На каждом из восьми агентов заранее выбраны первые по unit_id до 12 dev
с дефектами, 12 нормальных и 2 с ничьей панели. Это усиленный диагностический
срез, а не оценка реальной распространённости дефектов. Все голоса неизменны;
gold участвует только в выборе заранее фиксированного среза и подсчёте метрик.
Смена только человеческой метки не меняет отправляемый контекст (тест).
Baseline/candidate чередуются; ошибки кешируются без замены, единицы
сохраняются в знаменателе coverage. Новые test-запросы не делаются.

Никакой профиль не принимается по одному среднему κ. Сначала сравниваются
пары и конкретные исправленные/испорченные решения, затем полные dev
затронутых агентов и отдельная проверка переноса.

## H3: слепая классификация перед сравнением (до API)

Для CI09997438 целевая оценка — правильность маршрута. Вместо суждения о
показанном маршруте GigaChat самостоятельно выбирает одну из 14 категорий,
получая только текущий вопрос, прошлые QA и исходную инструкцию классификатора.
Текущий ответ, наблюдаемый маршрут и gold до модели не доходят (тест).
Код сравнивает результат с observed_prediction. Отказ остаётся отказом.
Модель не обучается; объяснение короткое, native function calling.

Полный dev: 71 единица / 142 сравниваемых ответа; 17 baseline уже есть в H1.
Те же Max, T/P/max_tokens. Основной контроль — baseline исходного judge на
этих же единицах. Человеческие метки не заменяются. В исходном xlsx точное
сравнение observed class с GT совпадает с итоговой меткой на 71/71 dev и

не исправляются и не используются как примеры классификации.

Это изменение способа решения задачи маршрутизации. Оно не заменяет оценку
качества ответа у других агентов, где маршрут лишь один из нескольких критериев.
Проверки: 140 passed, ruff clean. Решение о качестве — после всех 71 пар.

## Что показали восстановление и экспертные объяснения

**H2 завершён: улучшения нет.** Все 106 ответов валидны. На полном dev
CI09840670 κ = −0,0334, ordinal α = −0,0606, ρ = −0,0495 в обоих плечах.
Из 53 решений изменились два: один FP исправлен, другой добавлен. Остались
6 FP из 52 нормальных, единственный дефект пропущен. Accuracy 46/53=86,79%,
train-mode baseline 52/53=98,11%. Утрата scenario реальна, но её восстановление
не объясняет и не устраняет эти ошибки исходного judge.

**ПОСТ: асессор и эксперты по-разному исполняют смысл «структуры».**
Проверены исходные комментарии с точным совпадением версии ответа. На dev
структурных 0 — 4, из них 3 единогласных; структурных 1 — 14, из них 8
единогласных. У всех 18 есть экспертные объяснения. Ниже обезличенные случаи:

- Аккуратно оформленный отказ найти сведения о налогообложении получил 0
  у всех экспертов: они нашли сведения в пояснении клиента. Judge видит только
  пустой search_case_docs `[]`. Это не задача распознавания списков/Markdown.
- Нумерованный ответ о персональных сведениях перечисляет данные из других
  типов документов и лишь внутри списка сообщает об отсутствии нужного
  документа. Эксперты единогласно ставят 0 структуре, указывая потерю логики
  относительно запроса. Аналогичная трактовка есть в примере самой рубрики.
- Внешне последовательный вывод о выплате зарплаты строится из платежей
  за услуги. Эксперты указывают подмену экономической роли; структура 0/0/1.
- Короткий отказ из-за отсутствующего документа получает 2/2/2, если документ
  действительно отсутствует. Автоматическое «любой отказ = 0» неверно.

В 37 из 492 активных единиц ПОСТ весь evidence состоит из пустых результатов
инструментов: train 12, dev 6, test 19. На dev пять из шести имеют 2/2/2,
один 0/0/0 по консенсусу. `[]` доказывает отсутствие находки конкретного поиска,
а не отсутствие документа. Подсчёт «есть непустая строка evidence» завышает
доступность фактов. Даже восстановление tool results не заменяет полный
пакет источников, доступный экспертам.

Тэги записаны общим полем на несколько критериев: наличие #Ложь рядом со
структурой не позволяет автоматически приписать ей фактическую ошибку.
Отчёт сохраняет их как shared_unit_tags; выводы выше опираются на сами
комментарии и рубрику. Все human gold остаются исходными.

Дополнительно найдены буквальные совпадения длинных ответов с примерами
рубрики: ПОСТ 2 test; CI09877398 4 train / 2 dev / 11 test. Это сигнал для
аудита шаблонных ответов, а не доказательство утечки всего теста: канонический
ответ может быть прямо предписан инструкцией. Оценки не исключались постфактум.

## Что требуется изменить для production

1. **Источник фактов.** Для проверки документов judge должен получать
   подтверждённые сведения/инвентарь того же пакета и версии. Кеш поиска с
   пустым результатом недостаточен. Ретроспективное объединение соседних
   вопросов уже проверялось в packet_round; оно не доказывает доступность
   этих сведений в момент исходного ответа. В источнике date_create бывает
   строкой nan, а answer_time — длительностью, не временем события.
2. **Исполнение рубрики.** Разделить проверку оформления, соответствия
   запросу и логических ролей; итог собирать по исходным правилам, сохраняя
   их приоритеты. Не переименовывать существующую human-структуру в чистую
   читаемость и не выдавать изменённый target за прирост на прежнем gold.
   Коллапс всех извлечённых признаков в максимум не лечится сменой порогов.
3. **Подготовка production input.** `_assessor_units` передаёт только
   required_evidence. Произвольные optional ключи не описаны контрактом;
   packed dialogue размножает session extras на каждый turn и может принести
   будущую history. Простое копирование всех полей не является корректным
   ремонтом. Для восстановленных источников provenance доказан специальным
   кодом; для произвольного production UMR — пока нет. evaluation_ready не
   обходится. Семантические scenario/subscenario пока не опубликованы в
   контракте production turns.
4. **Разные задачи — разные проверки.** Для маршрутизации проверяется H3
   (независимое решение + сравнение), для документов необходим источник фактов,
   для ordinal-оценок — проверка конкретных границ 0/1/2. Удачный маршрутный
   judge не объявляется улучшением фактичности других агентов.

## Как это соотносится с приложенным исследованием и статьями

[RULERS](https://arxiv.org/abs/2601.08654) предлагает фиксировать трактовку
рубрики, привязывать суждения к проверяемым свидетельствам и отдельно
калибровать шкалу. Это полезное направление для найденного расхождения смысла
критерия, но само наличие цитаты ещё не доказывает верность вывода.

[Does task decomposition improve automatic NLG evaluation?](https://arxiv.org/abs/2609.01139)
не находит преимущества декомпозиции над честным контролем в рассмотренных
задачах; авторы связывают прежние выигрыши с использованием human training
labels. Поэтому повторение checklist без контроля информации не считается
обоснованным следующим улучшением. Наш отрицательный feature-контроль
согласуется с риском, но не является репликацией этой статьи.

[JudgeBench](https://arxiv.org/abs/2410.12784) показывает трудности judge на
сложных задачах корректности. Сильная генеративная модель сама по себе не
гарантирует качество оценщика. H3 проверяет независимое решение именно там,
где задача допускает точное сравнение результата.

[karpathy/autoresearch](https://github.com/karpathy/autoresearch) полезен как
образец цикла фиксированный контроль → одна гипотеза → измерение → сохранение
или отклонение. Его GPU-training loop не является готовым оценщиком LAIM.
Здесь сохраняются код, протоколы, отрицательные результаты и SHA; оптимизация
по многократно просмотренному test не выдаётся за независимую валидацию.

Транспорт H3: после трёх ConnectError серия прервана. Отдельный curl-контроль
показал зависание TLS 1.2 и для OAuth, и для API; стандартный TLS получил
ожидаемые HTTP 405 (OAuth без POST) и 401 (API без авторизации). Только для H3
снято принудительное ограничение TLS 1.2; модель/сообщения/температура неизменны.
Новый transport_profile включён в cache identity; предыдущие ошибки сохранены.
Это повтор после ремонта соединения, а не отбор удачных ответов модели.

## H3 завершён; H4 — использование потерянной train-разметки категорий

H3 после ремонта TLS: 71/71 транспортно валидный ответ, 4 not_assessable.
На полном dev CI09997438 исходный judge: κ=0,114, ordinal α=0,119,
ρ=0,114; 1/5 найденных дефектов и 5/66 ложных тревог. Слепая классификация:
κ=−0,095, ordinal α=−0,090, ρ=−0,097; 0/5 найденных дефектов, 7/66 ложных
тревог, 4 отказа на нормальных случаях. Гипотеза отклонена: самостоятельное
решение повторяет все пять ошибочных маршрутов. Одной независимости от
показанного маршрута недостаточно.

H4 зафиксирован до API: тот же слепой классификатор без примеров против
шести ближайших BM25 train-примеров с **правильной исходной категорией GT**.
Прежняя корзина сохраняла только binary assessment_score и не использовала
этот более подробный сигнал. Вход примера: вопрос, прошлая история, правильная
категория; текущий ответ и наблюдаемый маршрут исключены. Из 207 train
доступны 204 валидных GT; три числовых GT не угадываются и не исправляются.
Границы классов берутся из исходной инструкции, не переписываются под dev.

Тот же полный dev из 71 единицы. Контроль H3 переиспользуется только по
точному request hash, включая профиль транспорта; новых H4 запросов 71.

## Согласие людей и интерпретация метрик

Пересчитана Krippendorff α на исходных индивидуальных голосах с пропусками,
без подмены панели консенсусом:

| Панель / критерий | α nominal | α ordinal |
|---|---:|---:|
| ПОСТ / полнота | 0,669 | 0,738 |
| ПОСТ / фактичность | 0,577 | 0,658 |
| ПОСТ / структура | 0,468 | 0,541 |
| Онлайн / структура | 0,624 | 0,701 |

ПОСТ: 492 единицы, 6 идентификаторов экспертов; 389 единиц с тремя голосами,
102 с двумя, одна с одним. Онлайн: 1000 единиц, три анонимных слота; идентичность
разметчиков не подтверждена. В остальных шести корпусах независимой панели нет.

[Krippendorff](https://repository.upenn.edu/bitstreams/b6ea3a5b-3dee-4f27-a159-e44393eda7d4/download)
предлагает α≥0,8 для надёжных выводов, 0,667–0,8 — для предварительных.
Это ориентиры надёжности разметки, а не универсальный SLA для автоассесора.
Согласие judge с majority gold может превышать inter-human α: числа панели
не являются математическим потолком качества модели.

Низкое согласие людей не оправдывает коллапс judge: в H1 он пропустил
**5 единогласно размеченных структурных дефектов ПОСТ и 7 Онлайн**, выдавая 2.
Есть одновременно проблемы разметки/трактовки и реальные ошибки модели.

Accuracy — доля точных совпадений, но при редком дефекте она поощряет
постоянный максимум. Мода выбирается только по train и затем фиксируется.
На том же полном наборе с известным gold сравниваются correct_label_yield,
recall дефектов, FPR и coverage; accuracy на подмножестве валидных ответов
показывается отдельно. Для H3 baseline mode на всех 71 равен 66/71=92,96%,
а не меняется от того, что candidate отказался на четырёх нормальных случаях.
κ=(observed−chance)/(1−chance); при постоянном максимуме κ=0, а Spearman
не определён. Это не округление до нуля и не доказательство случайности
каждого ответа. [Исследование prevalence и κ](https://pmc.ncbi.nlm.nih.gov/articles/PMC5712640/)
объясняет влияние дисбаланса; оно не отменяет необходимость находить дефекты.

## Исправление production-диагностики

В `agent/asessor_agent.py` прямой GigaChat теперь сохраняет различие между

не меняются. Это исправление наблюдаемости, не прирост качества модели.
Проверены реальный native parser без API, единственность вызова при blacklist,
успешные/неоценимые/неразбираемые ответы. Полный набор: 150 passed.

Три плеча, всего 450 новых запросов GigaChat-2-Max (T=P=.001, max_tokens=1800):
1. Pointwise control: те же reference с исходными числовыми метками.
2. Pairwise: метки скрыты, left_worse/equal/left_better/not_assessable
   для сравнения текущего объекта с каждым reference по каждому критерию.
3. Pairwise reverse: обратный порядок объектов и направлений пар.

Баллом становится единственное значение исходной шкалы с минимумом
противоречий наблюдаемым сравнениям; при равенстве минимумов или отсутствии
сравнений — отказ. Никаких подгоняемых на dev порогов. Отдельно рассчитывается
вариант, принимающий только совпавшие итоговые баллы двух порядков.
Все отказы учитываются в coverage/yield/recall, отдельная стабильность
сравнений не подменяет agreement с human. Метрики диагностического среза
не выдаются за частоты production. При успехе требуется полный перенос.

Pairwise не объявляется заведомо лучшим: исследования обнаруживают
[чувствительность протокола к нерелевантным изменениям](https://arxiv.org/abs/2504.14716)
и [позиционное смещение](https://arxiv.org/abs/2406.07791). Поэтому нужен
контроль на одинаковых reference и обязательная перестановка. Это проверка
архитектурной гипотезы, а не подтверждение результатов статьи на GigaChat.

## Бизнес-КМ ПОСТ: существенное расхождение цели оценки

Первичный `dev_report_303697.docx`, параграфы 65–67 и 115 (нумерация
`Document(...).paragraphs` с нуля), требует среднее экспертных оценок внутри
примера, нормирование /2 и F1=2FC/(F+C) после усреднения F и C. Это не
classification F1. Порядок весов исходного отчёта не полностью воспроизведён:
среднее всех экспертных строк и равные веса примеров различаются при разном
числе голосов. Исходный расчётный notebook не найден.

| Совокупность / веса | F | C | S | Бизнес-F1 |
|---|---:|---:|---:|---:|
| Все 3038 валидных raw-голосов | .780283 | .743746 | .801679 | .761577 |
| Активные 492 units, 1372 голоса равновесны | .728499 | .690962 | .756195 | .709234 |
| Активные 492 units, каждый пример равновесен | .722561 | .685976 | .747121 | .703793 |

Опубликованное .762 близко воспроизводится на всей raw-корзине. Но там
1115 разных ключей исходного примера; research имеет 494 units, из них
2 excluded_duplicate. Подготовка требует разбираемый response и точное
соответствие human/AI конечному вопросу/ответу. Поэтому сравнивать .762
со средним judge на отобранных 492 или dev63 напрямую некорректно.
Фильтрация меняет совокупность, что видно уже на человеческой оценке.

На одних и тех же 430 units с уникальной модой всех критериев business-F1
из средних экспертов равен .715503, из мод — .707210. Смена среднего на
моду тоже меняет оцениваемую величину. Mean(unit harmonic) также неверен:
на raw .744788 против правильного harmonic(mean F, mean C)=.761577.

`business_metric.py` отдельно оценивает текущий dev63 с равными весами
объектов и средними голосов, включая ничьи моды. Human business-F1=.764221.
По общим 50 отвеченным объектам всех четырёх плеч human=.821582:

| Профиль | Бизнес-F1 на тех же 50 | Смещение |
|---|---:|---:|
| Max, обычные примеры H6 | .879545 | +.057963 |
| Max, +экспертные комментарии | .913661 | +.092079 |
| Max, совместимые примеры H7b | .879545 | +.057963 |
| Ultra, те же совместимые примеры H8 | .964767 | +.143185 |

На полном dev63 неизвестные ответы можно ограничить допустимыми 0…1
без подстановки удобного значения. Для H7b business-F1 находится в
[.848910; .896544], для H8 — [.943844; .959727]. **Даже нижняя граница
выше human .764221:** завышение нельзя объяснить только исключением отказов.
Это прямое подтверждение риска завышения бизнес-КМ, дополнительно к низким κ/α.

На собственных matched cohorts смещение H7b +.111155, групповой 95% CI
[.019122; .159793]; H8 +.187899, CI [.061055; .243583]. Интервалы условны
на ответившем подмножестве, dev имеет только 7 групп. Константа из средних
**train** даёт .675722 на полном dev (смещение -.088499); это отдельный
aggregate baseline, который вообще не обнаруживает отдельные дефекты.

Текущий production main ожидает один assessment_score (`main.py:648`),
а supported scoring methods не содержат глобального harmonic (`measurement.py:22`).
Усреднение одного локального main_metric не воспроизводит эту нелинейную
агрегацию. Реальное утверждённое ПОСТ v3-definition не найдено; сохранённый
processed reference UMR не содержит main_metric/трёх исходных критериев.
**Нельзя объявлять component research полным production-прогоном бизнес-F1.**
Для такого внедрения необходимо согласованное определение и агрегация F/C;
в этой серии контракты соседних нод не менялись.

## Дополнительные проверенные ошибки на остальных агентах

У CI09997554 два пропущенных H1 дефекта содержат в клиентском ответе
внутренние справочные чанки и явно названные скрытые идентификаторы.
Человеческий gold=0 согласуется с прямым запретом технических деталей
в исходной инструкции. Это ошибка judge на наблюдаемом тексте, не отсутствие
внешнего знания. Простой фильтр по заголовку FAQ небезопасен: в test есть
положительный пример с таким заголовком. Точная строка про скрытый ID
встречается лишь в 3 dev-примерах, без train/test подтверждения переноса.
Постфактум правило для этих трёх не выдаётся за универсальный ремонт.

У CI09877398 есть ложные дефекты на уточняющих репликах, положительно
оценённых экспертами; критерии смешивают итоговую завершённость и допустимый
шаг диалога. Есть и спорные положительные многоходовые диалоги с переходами
между продуктами. Это требует проверки фазы диалога/исходных экспертных
пояснений; нельзя автоматически считать все расхождения ошибкой judge.
В исходной инструкции положительные и отрицательные примеры сами требуют
разного клиентского контекста, которого в research-input нет.
