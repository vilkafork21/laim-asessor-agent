# Ассесор LAIM: что действительно показывают метрики

Дата проверки: 11 сентября 2026 года. Анализ исходников, локальных данных, сохранённых ответов и исследовательских материалов. Новых вызовов LLM в этой проверке не было. Исходники production-нод не изменялись.

**Вывод:** имеющиеся результаты не подтверждают универсальную пригодность судьи. Некоторые реальные конфигурации проигрывают константе по точному совпадению меток, но превосходят её по обнаружению дефектов. Другие дают слишком много ложных дефектов либо пропускают большинство настоящих. Сводить это к одному сравнению accuracy с модой некорректно. Значения κ/α около нуля имеют несколько разных причин: реальный слабый сигнал, перекос классов, искусственные/противоречивые цели и ошибки отдельных версий scorer. Все эти причины обнаружены в доступных материалах.

**О текущей версии:** снимок `monitoring/laim-asessor-agent` совпадает с исследовательской линией `f31e0b1` и существенно исправлен относительно старых пакетов. Более свежий по дате ZIP `laim-asessor-agent-single-llm-model.zip` содержит другую, более старую по логике линию. Из локальных файлов нельзя установить, что именно сейчас развёрнуто на Sber DS. Исторические Haiku/Luna-оценки не являются измерением качества нынешнего GigaChat-3-Ultra с текущей рубрикой.

## 1. Что должен измерять ваш судья

У LAIM две разные задачи: оценить ответы/решения агента на отдельных обращениях и по этим оценкам измерить КМ и её динамику. Для этого судья должен воспроизводить **утверждённую итоговую человеческую оценку той же единицы**, имея данные, необходимые для применения рубрики.

Единицей может быть отдельный ответ, текущая реплика с историей либо целый диалог. У классификатора наблюдаемое действие — выбранная категория, у отвечающего агента — пользовательский ответ. Для фактической проверки нужны соответствующие документы, состояние клиента, результаты инструментов и время их актуальности. Отсутствие этих данных нельзя исправить высокой уверенностью LLM.

Здесь нельзя смешивать три значения слова accuracy:

1. **Бизнес-accuracy агента:** например, доля правильно выбранных маршрутов относительно истинного маршрута.
2. **Accuracy судьи:** доля случаев, где оценка судьи точно совпала с итоговой человеческой оценкой качества.
3. **Средняя КМ:** например, доля качественных диалогов или средняя релевантность 0–2, возможно с частотными весами.

Если judge сказал «ответ плохой», а человек сказал «ответ плохой», это повышает accuracy судьи и одновременно понижает оценку качества агента. Большое значение первой не означает хорошего качества второго.

В исследовательском коде это различие уже отражено: один `assessment_score`, явная рубрика, допустимые значения, направление качества, граница дефекта и обязательные свидетельства. [Описание контракта](/Users/antonzyukov/laim/monitoring/laim-asessor-agent/README.md:3), [реальный scorer](/Users/antonzyukov/laim/monitoring/laim-asessor-agent/agent/score_results.py:11).

## 2. Как сейчас считается baseline моды и что с ним не так

Для пар, на которых judge ответил, текущий scorer вычисляет:

\[
Accuracy=\frac{\sum_i \mathbf{1}(\hat y_i=y_i)}{n},\qquad
B_{holdout}=\frac{\max_c\#\{i:y_i=c\}}{n}.
\]

То есть `baseline_mode_accuracy` — доля самого распространённого человеческого ответа **на оцениваемом holdout, причём на подмножестве с ответом судьи**. Это непосредственно `observed_human.value_counts().max() / n` в [score_results.py](/Users/antonzyukov/laim/monitoring/laim-asessor-agent/agent/score_results.py:57).

Пример: из 100 человеческих меток 95 равны «хорошо», 5 — «дефект». Константа «всегда хорошо» получает 95% accuracy, не читая ничего. Это полезная проверка: модель может выглядеть точной просто из-за состава данных.

Но текущая мода выбрана после просмотра проверочных меток. Это **лучший константный ответ на данном holdout**, описательный ориентир с доступом к его истине. Такой показатель допустимо публиковать с этим названием. Его нельзя без оговорки представлять результатом обученного baseline.

Обычный проверяемый baseline устроен так:

\[
c^*=\arg\max_c\#\{i\in train:y_i=c\},\qquad
B_{train\to test}=\frac1{|test|}\sum_{i\in test}\mathbf{1}(y_i=c^*).
\]

Класс выбирается только на train; правило разрешения равенства частот фиксируется заранее. Именно обучение на `y` описано для `DummyClassifier(strategy="most_frequent")` в [документации sklearn](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyClassifier.html). На трёх подробно восстановленных реальных запусках train-мода и holdout-мода дали одинаковую accuracy. **Их проигрыш по exact accuracy не исчезает от исправления определения baseline.**

Есть ещё две методологические проблемы:

- При отказах judge меняется состав пар, а вместе с ним и baseline. Два судьи могут сравниваться с разными константами на разных задачах. Для сравнения нужны фиксированный полный holdout, отдельное покрытие и явно обозначенные метрики на парах.
- Мода — правильный константный ориентир для потери «совпал/не совпал». Для абсолютной ошибки числового score нужен также train-медианный baseline; для квадратичной — train-среднее. Среднее вроде 1.728 не является допустимой меткой шкалы 0/1/2: оно проверяет числовой прогноз/среднее, а не категориальную классификацию. [Константные регрессионные стратегии sklearn](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyRegressor.html).

В старых версиях есть дополнительная неоднозначность: `Mean accuracy` иногда означает нормированную близость чисел, а не точное совпадение. В архивном тесте одни и те же три пары дают 0.8333 по старой близости и 0.6667 по exact accuracy. Кроме того, старый многокритериальный scorer сначала усредняет совпадения доступных критериев внутри строки, потом строки. Это не совпадение всех критериев сразу и не обязательно совпадение итоговой КМ. Сравнивать исторические колонки по одному названию нельзя. [Архивные результаты](archive_probes.json), [старый расчёт](/Users/antonzyukov/laim-artifacts/asessor-explicit-model-id/agent/score_results.py:129).

### CI09997554: проигрыш по accuracy и польза в поиске дефектов одновременно

Дефект = человеческая оценка 0. Матрица после повторной оценки:

| Истина | Judge: дефект | Judge: хорошо |
|---|---:|---:|
| Дефект | 3 | 1 |
| Хорошо | 6 | 47 |

| Свойство | Judge | «Всегда хорошо» |
|---|---:|---:|
| Точные ответы | 50/57 | 53/57 |
| Обнаруженные дефекты | 3/4 = 75% | 0/4 = 0% |
| Ложные тревоги | 6/53 = 11.32% | 0/53 |
| Доля настоящих дефектов среди тревог | 3/9 = 33.33% | Не определена: тревог нет |
| Balanced accuracy | 81.84% | 50% |
| Оценённая доля качественных единиц | 48/57 = 84.21% | 100% |
| Ошибка относительно человеческих 53/57 | −8.77 п.п. | +7.02 п.п. |

Balanced accuracy усредняет recall классов и поэтому не даёт многочисленному классу полностью определять результат. Для бинарной задачи это `(recall дефектов + recall нормальных)/2`. [Определение sklearn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.balanced_accuracy_score.html).

Имеется простое сравнение практической цены ошибок. Если пропуск дефекта стоит `C_FN`, а ложная тревога `C_FP`, то потери на этих 57 единицах:

\[
L_{mode}=4C_{FN},\qquad L_{judge}=C_{FN}+6C_{FP}.
\]

На этой выборке judge выгоднее константы, когда **пропуск стоит больше двух ложных тревог**. Это арифметический порог по наблюдённым ошибкам, а не установленная бизнесом стоимость и не гарантия для будущего потока.

75% recall здесь означает всего **3 находки из 4**. Даже при оптимистичном предположении независимости точный 95%-й биномиальный интервал составляет примерно **19.4–99.4%**. Групповые зависимости могут дополнительно ослаблять вывод. Убедительного доказательства требуемого recall здесь нет.

Повторная оценка в этом запуске сократила FP с 14 до 6, сохранив TP=3. Она повысила accuracy с 73.68% до 87.72%. Это наблюдение не переносится автоматически на другие задачи.

### CI09774440: почему порядковую шкалу нельзя описывать одним accuracy

Для варианта `_final` человеческие метки: 0 — 4, 1 — 5, 2 — 33. Матрица **строки — человек, столбцы — judge**, порядок меток 0/1/2:

```text
           judge 0   judge 1   judge 2
human 0       1         2         1
human 1       0         3         2
human 2       0         8        25
```

| Показатель | Judge | Train-мода = 2 | Train-среднее = 1.72785 |
|---|---:|---:|---:|
| Exact accuracy | 69.05% | 78.57% | Не является меткой шкалы |
| MAE, в единицах шкалы 0–2 | 0.33333 | 0.30952 | 0.46504 |
| MSE | 0.38095 | 0.50000 | 0.40559 |
| Ошибка среднего | −0.04762 | +0.30952 | +0.03737 |

Judge проигрывает моде по accuracy и MAE, но делает меньше квадратично взвешенных ошибок и гораздо меньше смещает среднюю КМ, чем константа 2. При этом историческое train-среднее на данном holdout предсказывает среднее ещё ближе. Последнее не доказывает, что оно способно обнаруживать будущую деградацию: константа не реагирует на новые ответы.

По трём классам balanced accuracy судьи 53.59%, у моды 33.33%. Диагностическая quadratic weighted κ = 0.443, nominal κ = 0.292. Они отвечают на разные вопросы: точная категория и ошибка с учётом расстояния. Выбирать веса после просмотра результата ради большей κ нельзя.

Если дефект означает **любую оценку ниже 2**, judge находит 6 из 9, precision=6/14=42.86%. Если отдельно интересует именно самая низкая категория 0, находит только 1 из 4. Это разные определения события; порог периодной КМ 1.65 не становится автоматически границей дефекта отдельного ответа.

Повторная оценка в этом запуске изменила recall категории 0 с **3/4 до 1/4**, а MAE с 0.28571 до 0.33333. Значит, механизм пересмотра может помогать на одной задаче и ухудшать профиль ошибок на другой.

### Что можно сказать о статистическом проигрыше

Наблюдаемые accuracy ниже моды. Но небольшие holdout не доказывают устойчивый проигрыш в популяции. Диагностический bootstrap разности accuracy даёт для `_final` 440 примерно [−26.2; +4.8] п.п., для 554 [−19.4; +7.1] п.п. Оба интервала включают ноль.

Это исследовательские интервалы: использованы доступные group ID, при их отсутствии — точный контекст; мода holdout фиксирована при повторных выборках. Они не учитывают настройку на уже просмотренном holdout, полную зависимость клиентов и перенос на другие периоды. Корректная формулировка: **на этих данных есть наблюдаемый проигрыш по exact accuracy и нет доказанного превосходства; универсальный статистический вывод не установлен**.

## 5. Почему κ и α могут быть около нуля

### Нормальный статистический эффект

Каппа Коэна:

\[
\kappa=\frac{p_o-p_e}{1-p_e},\qquad p_e=\sum_c p_{human}(c)p_{judge}(c).
\]

`p_o` — фактическое совпадение, `p_e` — совпадение при независимом выборе меток с наблюдаемыми распределениями человека и судьи. Поэтому κ=0 означает отсутствие превышения **этой** модели случайного согласия, а не ноль правильных ответов. [Определение и варианты весов](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html).

У «всегда хорошо» на 95 хороших/5 плохих `p_o=p_e=.95`, поэтому κ=0 при accuracy=.95. Для двух номинальных рядов на тех же 100 единицах α≈−.0205. Это воспроизведено тестом, не является ошибкой библиотек и не свидетельствует о случайных сбоях модели.

Каппа не вычисляется как `(accuracy - accuracy_mode) / (1-accuracy_mode)`: в её ожидаемом согласии участвует также распределение предсказаний judge. Поэтому κ=.404 при accuracy судьи ниже моды в 554 не содержит противоречия.

Альфа Криппендорфа имеет вид `α=1−D_o/D_e`, сравнивая наблюдаемое и ожидаемое несогласие. Она использует другую модель ожидаемого несогласия, допускает несколько разметчиков, пропуски и разные шкалы расстояний. Здесь runtime явно использует **nominal**, то есть любые разные метки считаются несовпадением. [Описание автора](https://www.asc.upenn.edu/sites/default/files/2021-03/Computing%20Krippendorff%27s%20Alpha-Reliability.pdf).

Для двух рядов κ и α нередко близки, но не обязаны совпадать, особенно при существенно разных частотах оценок. По документированной матрице 670 честно получаются κ=.057 и α=−.252; пересчёт по частотам подтвердил оба числа. Положительная κ и отрицательная α здесь не означают перепутанные оси.

Одноклассовый вырожденный набор, недостаток пар или отсутствие ответов требуют `null/не определено`, а не произвольного нуля. Нулевая определённая κ и невозможность её вычислить — разные состояния.

### Реальная ошибка старого scorer

В сентябрьском ZIP κ считается напрямую по числам 0/0.5/1. Библиотека отвергает их как непрерывную цель; исключение подавляется, а отсутствие вычисленных значений превращается в 0.0. [Место ошибки](/Users/antonzyukov/laim-artifacts/asessor-explicit-model-id/agent/score_results.py:80), [подмена отсутствия нулём](/Users/antonzyukov/laim-artifacts/asessor-explicit-model-id/agent/score_results.py:194).

Контрпример: человеческий и судейский ряды **идеально одинаковы**, значения 0/0.5/1. Получается accuracy=1, α=1, **κ=0 вместо 1**. В 1000 случайных сравнений с независимым расчётом этот пакет ошибся в 498, главным образом на дробных метках. У dev и исследовательского scorer этот дефект уже исправлен. Для двух восстановленных исторических дробных запусков κ=0 пересчитывается примерно в .0755 и .1064: исправление убирает ложный точный ноль, но не создаёт сильное согласие.

### Синтетическая цель местами не выводится из текста

В старом генераторе текст и качество выбирались независимо случайным образом. В более новом бинарный признак частично связан с текстом, но отдельные дробные/критериальные значения по-прежнему случайны. Повторяемые шаблоны создают одинаковый вход с разными метками. [Старый генератор](/Users/antonzyukov/laim-simulation-run-20260902.DN8o0G/generator/basket.py:83), [другая линия генератора](/Users/antonzyukov/laim-simulation/generator/basket.py:105).

В 124 сохранённых синтетических запусках с обеими метриками: 9 побед по accuracy, 62 равенства, 53 проигрыша; κ ровно 0 в 93; recall дефектов 0 в 101. Эти числа описывают зависимые сценарные запуски, а не 124 независимых реальных агента. [Сводка](synthetic_summary.json).

В 91 сопоставленном запуске конфликтует именно полный `assessment_context`, а не только проекция «вопрос–ответ». Пример `luna10s24_CI11899183_300006`: 40 единиц, 21 уникальный контекст; максимальная accuracy любого детерминированного ответа по этому контексту равна **95%**, ровно как мода. Ожидать победы над ней на таком holdout невозможно для детерминированного context-only judge. Случайная дополнительная информация не превращает независимую случайную метку в осмысленную цель.

Такая синтетика годится для проверки портов, обработки ошибок и сценарных ветвей. Она не годится как самостоятельная проверка семантического качества judge.

**BM25 воспроизводимо неверен**, а не просто «неудачно подобраны параметры». При raw scores `[2, 0, 1]` старый код выбирает лучшим документ с raw score 0. `argsort` возвращает перестановку индексов, которую ошибочно используют как ранг каждого документа. [Тесты](stress-research.json), [ошибка](/Users/antonzyukov/laim-artifacts/asessor-explicit-model-id/retriever/retriever.py:77).

**Усечение few-shot:** старый векторный путь сохраняет только первые 4000 символов, BM25 — полный пример, объединение идёт по тексту. Два исходных примера становятся тремя, причём к усечённому тексту остаётся gold полного диалога. Исследовательская линия сохраняет полный контекст. Этот воспроизведённый дефект не доказывает, что именно он вызвал конкретные FP: в исследовании S4b сохранённые few-shot проблемного 554 не были усечены.

**Пересмотр только низких оценок** в старой линии направлен на поиск оснований не штрафовать. Это меняет операционную строгость judge, а не гарантированно улучшает качество. Два реальных контрнаправленных эффекта показаны выше. В research этот механизм удалён; эффект новой конфигурации требует отдельной проверки, старые ответы его не измеряют.

**Остающиеся ограничения research:**

- `admission` не сравнивает accuracy с модой напрямую. Его `no_better_than_baseline` означает одновременное нарушение порогов recall и κ. Название сильнее реально проверяемого утверждения: это не статистический тест проигрыша моде. [admission.py](/Users/antonzyukov/laim/monitoring/laim-asessor-agent/admission.py:65).
- Прямых критериев допустимого FPR/precision и абсолютного смещения КМ в admission нет. Поэтому доступная цена ложных тревог или точность оценки средней КМ не гарантируются статусом допуска.
- Пороги по точечным recall/κ и минимальному числу групп — полезная эвристика, но не доверительная гарантия. При нескольких дефектах этого мало.
- Интервал `judge_bias` — нормальный интервал по парным разностям, без кластерного расчёта. Он не обосновывает перенос смещения на будущую смесь задач. [judge_bias](/Users/antonzyukov/laim/monitoring/laim-asessor-agent/admission.py:94).
- Метрики scorer равновесны по оценочным единицам. Частоты потока, отбор сессий и знаменатель периодной КМ — отдельная задача. Удаление дубликатов для независимой оценки judge не означает разрешение удалить реальные повторные обращения из КМ периода.
- `definition_id` фиксирует смысл оценки, но не полный набор model revision, prompt, содержимого RAG, embedding и транспорта. Для воспроизводимости нужна идентичность всей проверенной конфигурации.

Таким образом, **исследовательскую архитектуру нельзя назвать сломанной на основании старого κ=0; но нельзя назвать подтверждённо эффективной только потому, что её unit-тесты зелёные**.

## 8. Как правильно оценивать judge в LAIM

Минимальная содержательная карточка должна отвечать на четыре вопроса:

| Вопрос | Основные показатели | Почему одного accuracy недостаточно |
|---|---|---|
| Воспроизводит ли человеческие решения? | Матрица ошибок, exact accuracy и train-mode baseline; nominal κ как диагностика | Большинство может скрыть ошибки редкого класса |
| Находит ли значимые дефекты с приемлемой ценой? | TP/FN/FP/TN, recall всех дефектов, precision, FPR, поддержка класса; цена ошибок | Recall без FP допускает «всё плохо», accuracy без recall — «всё хорошо» |
| Насколько ошибается числовой score? | MAE; RMSE либо заранее выбранная weighted κ, если расстояния оправданы рубрикой | Ошибка 0→2 и 1→2 имеет одинаковую цену в exact accuracy |
| Правильно ли измеряет КМ и изменение качества? | Парное смещение на шкале КМ, ошибка агрегатов по независимым периодам/группам, интервал неопределённости | Высокое совпадение отдельных меток не гарантирует несмещённого среднего |

Обязательно рядом: полный `N`, число пар, число независимых групп, число дефектов по тяжести, coverage в целом и отдельно по дефектам/нормальным, распределения меток, версия рубрики/судьи. α исходной человеческой панели — отдельная диагностика качества gold, а не ещё один псевдонезависимый сертификат judge.

Для порядковой шкалы близость следует задавать осмысленно. Если 0/1/2 лишь упорядочены, quadratic distance не становится автоматически истинной стоимостью ошибки. Если шаги шкалы интерпретируются численно, MAE/RMSE полезны в её исходных единицах. Spearman показывает сохранение порядка, но может быть высоким при систематическом сдвиге всех оценок; он не заменяет проверку смещения.

AUROC/AUPRC, Brier score и калибровка вероятностей полезны только при наличии подходящей непрерывной уверенности/вероятности. Категория качества 0/1/2 сама по себе не является вероятностью правильности judge. Не следует добавлять эти метрики только ради большого списка.

**Протокол приёмки:**

1. Зафиксировать единицу, итоговую формулу человеческой КМ, шкалу, дефект по тяжести, обязательные факты и правила отказа. Разделить голоса людей и разные критерии. Разрешить предметные конфликты gold; не учить модель воспроизводить случайные/противоречивые метки.
2. Сделать независимый holdout по сессиям/клиентам/семействам задач и, где возможно, времени. Все настройки prompt, RAG и выбор модели делать на train/dev. Проверить точные и семантические дубликаты. Уже многократно разобранные 57 диалогов оставить исследовательским набором.
3. Зафиксировать baseline на train и сравнивать на тех же единицах. Отдельно иметь естественный состав данных для precision/КМ и обогащённый набор известных критичных дефектов для recall. Второй не подменяет первый; при отсутствии будущих частот честно публиковать показатели по пакетам.
4. Считать метрики по всем принятым ответам с явной областью `paired`; отказы сохранять. Recall должен включать все человеческие дефекты: отказ на дефекте не является его обнаружением. Если отказ запускает ручной разбор, дополнительно оценить итоговое качество и трудозатраты такого процесса.
5. До просмотра результатов установить приемлемые FN/FP и ошибку КМ. Для допуска проверять неопределённость этих величин, а не только точечные пороги κ=.2/recall=.5. Размер набора выбирать по нужной точности и числу независимых дефектов, а не универсальному минимуму строк.
6. Проверить повторяемость решений и отказов, длинные диалоги, недостаток фактов, инъекции в оцениваемом тексте, изменение доли дефектов, новые формулировки и версии документов. Разделять детерминированные тесты кода и реальные модельные испытания.
7. Финально проверить тот же judge/rubric/RAG/model/transport, который будет исполняться в monitoring. Не добавлять весь holdout в RAG после успешной проверки и не выдавать результат другой конфигурации за её допуск.

Это исправляет критерий оценки, а не пытается получить более красивую κ.

## 9. Почему для динамики КМ нужна отдельная проверка

Если КМ — средняя оценка с весами, то:

\[
K=\frac{\sum_iw_iy_i}{\sum_iw_i},\qquad
\widehat K=\frac{\sum_iw_i\hat y_i}{\sum_iw_i}.
\]

Нужна ошибка `K̂−K` при правильных весах и знаменателе. Приведённые выше −8.77 п.п. для 554 — ошибка **невзвешенного holdout**, не доказанная ошибка всего production-периода.

Для бинарного дефекта при истинной доле `π` и стабильных TPR/FPR доля судейских тревог:

\[
q=TPR\,\pi+FPR(1-\pi)=FPR+(TPR-FPR)\pi.
\]

По историческому 554 это приблизительно `q=.1132+.6368π`. При наблюдаемых 7.02% человеческих дефектов judge отмечает 15.79%. Если TPR/FPR действительно стабильны, изменение истинной доли передаётся с коэффициентом .6368. Константа «всегда хорошо» вообще не реагирует на изменение качества.

Формально обратная поправка `(q−FPR)/(TPR−FPR)` существует, но **применять её по четырём дефектам и переносить на будущие данные нельзя как доказанную калибровку**. Нужны достаточные данные, стабильность ошибок и оценка неопределённости. Простое вычитание старого среднего bias имеет те же ограничения переноса.

При отказах неизвестна часть score; удаление её веса даёт среднее только по отвеченным случаям. Если трудные/плохие обращения чаще вызывают отказ, оно смещено. Это необходимо отражать в КМ отдельно от agreement судьи.

Проверка нормализации и построения единиц research прошла 12 сценариев до 10 000 строк. При 10 репликах на сессию медиана трёх локальных измерений: qa≈0.742 с, history≈0.912 с, dialogue≈0.436 с. Это **только подготовка единиц**, без retrieval, сериализации всех запросов и LLM.

На одном диалоге из 1000 реплик полный контекст достигает 265 722 символов; режим истории создаёт суммарно 123 933 880 символов во всех оцениваемых префиксах. Сохранение полного контекста исправляет смысл, но не решает бюджет LLM. Нужен контролируемый бюджет целых примеров/единиц, не усечение с сохранением оценки полного диалога. [Нагрузка](load_probe.json).

Дополнительно проанализированы 6587 уникальных сохранённых payload: Haiku 485, Sonnet 450, Luna 5652. В 5512 обнаружен fallback на собственные знания; длина prompt p50=9763, p95=16666, максимум 77716 символов. Это наблюдения старых логов, не измерение нынешнего runtime. [Профиль](data_diagnostics_summary.json).

Канонические таблицы прочитаны полностью, широкая инвентаризация проверила схемы 1976 Parquet. Это не означает 1976 независимых человеческих тестовых наборов. Pickle не десериализовались в этой проверке; старые первичные ответы S4a/S4b не найдены. Без human gold нельзя измерить accuracy на monitoring traces. Платформенный SLA, инъекции и семантическая устойчивость текущего LLM новым живым прогоном здесь не проверены. В просмотренном окружении нет настроенного модельного HTTP-маршрута; значения секретов не выгружались.

Красный exit code старых стресс-проверок ожидаем: он фиксирует найденные дефекты, а не незавершённый запуск. Инвентаризация и сравнение ZIP воспроизводятся скриптами `inventory.py`, `version_inventory.py`, `probe_archives.py` в этом же каталоге. Пакеты и данные остаются вне Git; ничего не коммитилось и не публиковалось.

**Решение по доступным свидетельствам:** accuracy оставить как диагностическую метрику точного совпадения и сравнивать с корректно определённым baseline. Для допуска judge основными сделать профиль дефектов, покрытие и ошибку целевой КМ с неопределённостью. κ/α оставить средствами диагностики agreement и состава классов. Сначала определить и очистить задачу, затем оценивать зафиксированную конфигурацию на независимых данных. Ни отказ от accuracy, ни исправление формулы κ, ни смена модели сами по себе не устраняют доказанные проблемы данных и ложных дефектов.
