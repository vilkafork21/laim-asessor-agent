# Протокол сравнения GigaChat judge

Данные и разбиение фиксируются до первого запроса judge на реальном объекте. Источники ранее исследовались, поэтому этот тест является исследовательским групповым holdout, а не независимой внешней сертификацией. Состав и SHA-256 каждого корпуса: case_inventory.json. Версия исходного runtime: f31e0b1, ветка research/judge-gigachat-20260911. Генеративная модель во всех вариантах — GigaChat-3-Ultra; фактически возвращённая версия сохраняется в каждом ответе. Другие провайдеры не используются.

Единицы: исходный dialogue/turn/qa по утверждённому сценарию каждого агента. CI10071259 — отдельный ответ с фактичностью, полнотой и структурой 0/1/2 и независимыми голосами экспертов. Средняя экспертная оценка не превращается в категорию для exact agreement. Точные дубликаты контекста объединены в общую группу; одинаковые контекст и панель оценок учитываются один раз. Разделение по клиентам/сессиям/связанным контекстам, seed 20260911: три групповых фолда train, один dev, один test. Не перемещать трудные примеры после получения ответов.

Проверяемые гипотезы:

1. Полные фактические tool results улучшают проверяемость фактичности и полноты CI10071259 по сравнению с тем же запросом и ответом без инструментов. Порядок вызовов и принадлежность к ответу проверены. Инструменты не заменяют отсутствующий полный клиентский пакет документов.
2. Краткое обоснование по конкретному пункту инструкции с проверяемой цитатой помогает обнаруживать ошибки и контролировать необоснованные оценки; возможное ухудшение также публикуется. Это проверка протокола, а не просьба раскрывать внутренние рассуждения модели.
3. Образцы только из train помогают передать границы шкалы; оцениваются отдельно от изменения доказательств. Вариант без RAG называется zero-shot, а не полным текущим runtime. Для полноценного runtime использовать его исходный retrieval и неизменённые примеры.
4. Повтор, перестановка ключей JSON и добавление нерелевантного текста не должны существенно менять решения. Инструкция внутри оцениваемых данных не имеет права управлять judge. Изменённые объекты — отдельные стресс-тесты, им не приписывается исходный человеческий gold без обоснования инвариантности.
5. Одновременно temperature=0.001 и top_p=0.001 — проверяемая настройка, не доказанный дефект. Её изменение проверяется отдельным фактором при достаточном доступном лимите.

Сначала ограниченный dev-пилот и проверка валидности ответов. Выбор дальнейшего объёма зависит от доступности API и остатка токенов; ошибки транспорта не являются not_assessable. Конфигурация выбирается только на dev, после чего сравнение с исходной конфигурацией фиксируется на test. Не подгонять промпт по ошибкам test. При отсутствии улучшения не объявлять кандидата лучшим.

Для каждого агента отдельно: число единиц и групп, покрытие валидными оценками, abstention, confusion matrix, accuracy, macro recall/balanced accuracy, κ nominal, α nominal; на 0/1/2 дополнительно взвешенная κ и MAE/RMSE с явным допущением о расстояниях. Обнаружение дефектов: TP/FN/FP/TN, precision, recall с отказами в знаменателе, FPR. Для периода: смещение среднего и MAE против средней панели. Train mode фиксируется на train; его accuracy измеряется на тех же test-объектах и отдельно на полном наборе. Для среднего периода сопоставляются train mean и медиана для соответствующих функций потерь.

CI10071259: agreement с каждым экспертом и человеческая α на тех же объектах; consensus только для однозначной моды с явным учётом исключённых ничьих. Средняя оценка панели — цель для MAE/RMSE и bias, не класс. Первичная классификационная κ не считается по дробным средним. Периодная «F1» в исходном отчёте — гармоническое фактичности и полноты, не classification F1.

Неопределённость: парный bootstrap по клиентским/сессионным группам; доля вырожденных повторов сохраняется. Интервалы на 2–4 дефектах и семи группах CI10071259 не интерпретировать как достаточное доказательство надёжности. Без заданной стоимости ошибок и допустимых рисков не вводить универсальный порог κ или принудительно повышать согласие изменением gold/шкалы.

## Дополнения до открытия test, 12 сентября 2026

После просмотра dev добавлен `grounded_ids_bm25`: реальные пункты рубрики и поля текущего объекта получают идентификаторы, допустимые ссылки ограничены JSON schema. Это проверка механической привязки обоснований; существующая ссылка не доказывает истинность вывода. Дополнительно только для CI09840650/CI09840670 проверяется `_scope`: явное указание границ маршрута/ответа, применимости кнопок, представления UI и внешних фактов. Эти уточнения разработаны по ошибкам dev; это исследовательский подбор, не заранее зарегистрированная единственная гипотеза. Gold и разбиение не меняются.

Перебираются пять Ultra-вариантов для всех агентов, шестой `_scope` только для двух указанных. Затем лучший Ultra-протокол каждого агента сравнивается с GigaChat-3-Pro на тех же dev-объектах. Другие провайдеры не используются. Контроль без текущих tool results (`_qa`) для CI10071259 служит ablation и не участвует в выборе финального кандидата.

Правило выбора: сначала варианты с coverage ≥0,95 по каждому критерию, затем максимальная средняя nominal κ по критериям данного агента; равенство разрешается MAE и числом токенов. При отсутствии варианта с нужным покрытием сначала максимизируется минимальное покрытие. Неопределённая κ имеет служебный rank −1, но публикуется как null. Это техническое ранжирование кандидатов, а не промышленный допуск; оно не отменяет проверку достаточности свидетельств и допустимых ошибок.

`test-selection.json` записывается до первого test-запроса. На test сравниваются исходный zero-shot Ultra и выбранная конфигурация; при совпадении конфигураций один и тот же результат не запрашивается дважды. Подбора после test нет. Повторы, форматирование JSON, удаление top_p и инъекция проверяются отдельно на первых четырёх dev-объектах каждого агента в порядке SHA-256, без ручного подбора удобных примеров.

В раннем пилоте JSON-сериализация сортировала свойства схемы и меняла порядок «обоснование/оценка». Все 22 результата до перехода на постоянный HTTPX-клиент исключены из основных runs независимо от качества, сохранены в pilot-transport-runs и перечислены в transport-replay.json. Они повторяются с единым порядком свойств схемы. Это устранение смешения двух протоколов, а не выбор удачного повторного ответа. Последующие main/dev результаты используют единый HTTPX-протокол; повторяемость исследуется отдельно.

Ключ предоставляет chat Ultra/Pro, но все проверенные embeddings возвращают HTTP 402. BM25-плечи используют реальную реализацию лексического retriever и train-примеры, но не имитируют недоступный dense/hybrid retrieval. Данные, отсутствующие в traces, не подставляются из памяти модели. Модельные запросы выполняются последовательно из-за ограничения аккаунта на параллелизм.
