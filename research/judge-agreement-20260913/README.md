`fix/judge-agreement-research-20260913`. GigaChat — единственная модель judge.
Полный live-вызов через Asessor.run считается проверкой production-условий;

## Что означают целевые значения

Для Cohen κ известная шкала Landis–Koch относит 0,41–0,60 к умеренному,
0,61–0,80 к существенному, 0,81–1 к почти полному согласию. Авторы прямо
называют границы условными. Это ориентиры, а не универсальные нормы допуска.[1]

Krippendorff рекомендует α≥0,800 для надёжных выводов; 0,667–0,800 — только
для предварительных. Цена неправильного вывода и доверительный интервал имеют
значение: статистическая значимость отличия от нуля не доказывает надёжности.[2]
Наш прежний рабочий ориентир α=0,6 не следует выдавать за принятую норму.

Spearman измеряет согласованность ранжирования, а не точное совпадение баллов.
Единица может сочетаться с систематическим сдвигом всех баллов и нулевой accuracy.
При константном входе коэффициент не определён. Для него нет универсального
порога допуска автоассесора; его рассматриваем вместе с κ, ordinal α и ошибками
тяжести. Асимптотический p-value на небольших зависимых выборках не используем
как доказательство качества.[3]

Порог κ=0,2 в текущей ноде — минимальная настройка admission. Хорошее качество
им не устанавливается. Для этой исследовательской серии ориентир: κ≥0,6,
ordinal α≥0,8, recall всех дефектов≥0,8, обнаружение тяжёлых≥0,9, FPR≤0,05,
coverage≥0,99 на каждом агенте с достаточной поддержкой дефектов. Это цели,
достижимость которых не доказана. Высокое agreement не заменяет проверку
достоверности источников. Пороги production-ноды этой работой не изменены.

## Причина низких коэффициентов на сохранённых ответах

Пересчитаны все 58 полных SDK-сравнений из предыдущей серии с текущим
`agent/score_results.py`. Здесь одна единица имеет одну человеческую моду;
ничьи исключаются из сравнения с консенсусом, но сохраняются в coverage.

| Агент / профиль / критерий / test | Пар | κ | α nominal | α ordinal | Spearman |
|---|---:|---:|---:|---:|---:|
| CI10071255, исходный, S | 187 | 0,025 | −0,118 | −0,161 | 0,105 |
| CI10071255, observed Max, S | 191 | 0,328 | 0,293 | 0,171 | 0,277 |
| CI10071259, исходный, F | 77 | 0,036 | −0,166 | −0,202 | 0,118 |
| CI10071259, исходный, C | 77 | 0,154 | −0,020 | −0,034 | 0,278 |
| CI10071259, исходный, S | 79 | −0,049 | −0,256 | −0,266 | −0,132 |

Исходный S-judge CI10071255 использует классы 0/1/2 с частотами 0/6/181,
а люди на этих же парах — 28/49/110. При неизменных частотах предсказаний
максимально возможная κ равна лишь 0,101. Это аналитический предел при
известном gold, а не новый алгоритм: нельзя получить хорошую κ, продолжая
ставить почти всем максимум. У нового S-профиля частоты 0/31/160 против
человеческих 30/49/112; предел κ=0,462, а фактически κ=0,328.
Максимальный Spearman при его частотах≈0,717, фактический≈0,277:
остаётся и ошибка ранжирования тяжести. Двенадцать из 58 сравнений имеют
неопределённый Spearman; это не двенадцать нулевых корреляций.

Пример для проверки формул: человек [0,0,1,1], judge [1,1,2,2] дают
Spearman=1 и accuracy=0. Поэтому повышать только корреляцию недостаточно.
Низкую α нельзя скрывать переходом к более выгодному варианту шкалы.

Для accuracy сравнение с train-модой корректно, но проверяет только точные
попадания. Если 95 из 100 ответов имеют оценку 2, константа 2 получает
accuracy=95%, κ=0, α≈−0,021 и неопределённый Spearman. Все пять дефектов
она пропускает. Это воспроизведено текущим scorer на синтетическом примере.
В формуле κ=(p_o−p_e)/(1−p_e) здесь p_o=p_e=0,95. У α другая модель
ожидаемого разногласия, поэтому даже nominal α не обязана совпадать с κ.

Baseline выбирает **один балл на train**, затем неизменно предсказывает его
для каждого holdout-ответа. Выбирать самый частый балл самого holdout и
выдавать его за обученный baseline нельзя; это отдельный oracle-ориентир.
Сравнение accuracy делается на одинаковых парах, а рядом обязательно стоят
coverage и correct_label_yield полного потока, recall дефектов и FPR.

`audit_agreement.py` воспроизводит коэффициенты и верхние пределы из сохранённых
векторов, не вызывает API и не публикует индивидуальные ответы. Его self-check
проверяет константу, сдвиг шкалы и полный отказ. Сырые данные и подробные
результаты хранятся вне репозитория; их SHA256 сохранены в STATE.json.

## Следующая гипотеза: короткие ориентиры каждого уровня

Протокол зафиксирован до API в коммите `96a4a22`. Текущее состояние: COMPLETED; оба профиля отклонены.
Код: `anchor_experiment.py`.

Причина проверки — схлопывание шкалы к максимальному баллу. Вместо большого
набора похожих ответов подаются не более трёх полных реальных train-примеров:
по одному с однозначной человеческой модой 0, 1, 2. Выбор по BM25 вопроса
(если вопрос отсутствует — текста ответа); совпадающая group_id исключается.
Экспертные метки текущего ответа не используются. Общие клиенты без одинаковой
group_id этим правилом не исключаются; dev остаётся разведочным набором.

Два плеча используют один GigaChat-2-Max, одинаковые system-инструкцию,
исходную рубрику, текущий контекст, JSON Schema и параметры T=0,001,
top_p=0,001, max_tokens=1000. Отличается только список calibration_examples:
пустой у baseline, по одному примеру доступных классов у anchored. Модель
даёт краткое основание и оценку. Частоты примеров не являются целевой долей
дефектов. Факты примеров не переносятся между объектами.

Порядок плеч чередуется между единицами; запросы идут последовательно.
Контроль не равен исходному legacy-промпту: он проверяет добавление ориентиров
внутри одного нового профиля. Выборка dev63 CI10071259 и dev214 CI10071255;
первый этап — по два фиксированных первых unit_id каждого набора, затем
полные наборы при работоспособной схеме. Основной критерий этой проверки S.
Train-примеры берутся из собственной корзины каждого агента. Это перенос
процедуры при доступной train-калибровке, не zero-shot на невиданного агента.

Основные сравнения: κ, ordinal α, Spearman, покрытие, recall и FPR, отдельно
тяжёлые дефекты. Полный результат публикуется, даже если большинство ответов
невалидно. Ошибки не перезаписываются успешными вызовами. Все уже открытые
test остаются регрессионными; свежий test не расходуется на слабый dev-профиль.

### Диагностика поиска примеров до следующей смены промпта

`retrieval_diagnostic.py` фиксируется до расчёта на реальном dev. Сравниваются
18 заранее заданных комбинаций: BM25 по вопросу, ответу либо обоим;
голосование 1/3/5 ближайших train-примеров; исключение общей group_id либо
также общей клиентской компоненты. При равенстве голосов предпочтительна
train-мода, затем меньший балл; без соседей — train-мода. Все варианты
публикуются, лучший dev-вариант не объявляется подтверждённым результатом.
Baseline — константная мода только train, а не мода проверочной корзины.

Это диагностический классификатор без API, не итоговый judge: требование
GigaChat сохраняется. Проверка выясняет, несут ли ближайшие train-ответы
сигнал об экспертной оценке и зависит ли он от общего клиента.

### Дополнение по свежим первичным работам

- [SAJA, ACL Industry 2026](https://aclanthology.org/2026.acl-industry.45/):
  один вызов модели возвращает несколько признаков рубрики; небольшой
  калибратор обучается по человеческим меткам. Доступ к logits не нужен.
  Применимость к нам: GigaChat остаётся источником семантических признаков;
  калибровка обучается только на train и проверяется отдельно на новом клиенте.
  Это следующая гипотеза, а не выполненный эксперимент. Простое преобразование
  нынешней почти константной оценки не создаёт отсутствующее ранжирование.
- [Lifecycle / RART, Netflix, август 2026](https://arxiv.org/html/2608.18300v1):
  рубрику уточняют по расхождению оснований judge и человеческих объяснений,
  затем контролируют дрейф. Их обогащённый дефектами benchmark не равен
  распределению production. Для LAIM применим принцип проверки причины
  оценки: совпавший балл с выдуманным основанием нельзя считать полным успехом.
  Противоречивые экспертные комментарии у нас требуют отдельного арбитража.
- [Rubric Artifacts, препринт сентября 2026](https://arxiv.org/html/2609.02942v1):
  авторы проверяют зависимость judge от текста рубрики и реакцию на изменение
  ответа. Это обосновывает контролируемые изменения наших реальных ответов,
  уже начатые тестом полного повтора. Их результаты на других моделях и
  бинарных задачах не доказывают ту же причину ошибок GigaChat.

Метрики статей не подставляются в наш отчёт как ожидаемый прирост. Принимается
только измеренный результат на зафиксированных локальных данных и версиях.

### Зафиксированный протокол признаков и train-калибровки

`feature_calibration.py` реализует проверку по идее SAJA, без заявления
о точном воспроизведении статьи. Один GigaChat-2-Max через Asessor.run
возвращает шесть признаков: внутренняя непротиворечивость, обоснованность
вывода, релевантность, отсутствие повторов, читаемость и отсутствие
технического мусора. Внутренняя шкала признаков 0–4 или null. Итоговый
`assessment_score` по исходной рубрике 0–2 сохраняется отдельно.

Два заранее заданных статистических калибратора: multinomial logistic
regression C=1 без весов и с class_weight=balanced; поиска параметров нет.
Это не другая языковая модель. Единственный источник семантических признаков —
GigaChat; коэффициенты обучаются только по train. Неизвестный признак кодируется
−1. Отказ GigaChat от итоговой оценки и полностью неизвестные признаки
не превращаются в числовой ответ калибратора.

До отбора человеческой моды из train удаляются **все** компоненты клиентов,
присутствующие в dev. ПОСТ: 169 train-единиц до исключения ничьих, 150 после,
девять клиентских компонент; dev63. Онлайн: 513 до ничьих, 498 после,
466 компонент; dev214. Test не участвует в fit, признаках или отборе параметров.
Тест меняет gold dev и проверяет неизменность коэффициентов и предсказаний.

Сначала две train-единицы (`--limit 2`) для проверки схемы; затем полный
ПОСТ, после него Онлайн. Smoke не выдаётся за оценку качества. API-ошибки
контракта, авторизации и квоты останавливают прогон; сохранённые ошибки
не перезаписываются. Публикуются все три профиля: raw GigaChat, unweighted,
balanced, с coverage, κ, ordinal α, Spearman, recall и FPR. Человеческие метки
dev используются только после получения всех ответов. Успех на просмотренном
dev остаётся исследовательским и требует дальнейшего подтверждения.

### Проверка работоспособности схемы признаков

Исходный smoke расширен с двух до четырёх первых train-единиц из-за отсутствия
валидного ответа. Итог: 0/4, включая ConnectError и четыре полученных
`finish_reason=stop` с синтаксически неверным JSON. Посторонние символы
вставлены перед ключами; это не ошибка диапазона баллов. Ответы сохранены
без исправления и повторной выдачи за успешный прогон.

Подготовлен отдельный контроль `--schema-style flat`: у каждого признака
плоский enum [-1,0,1,2,3,4] вместо nullable integer с minimum/maximum;
неизвестное значение −1 вместо null. Рубрика, остальные инструкции, модель
и параметры генерации сохраняются. Сначала те же четыре train-единицы,
новый каталог `feature-flat-runs`. До валидной схемы полный прогон не начинается.
Причина сбоя nullable ещё не установлена; формат и семантику не смешиваем.

[Официальный SDK](https://github.com/ai-forever/gigachat/blob/main/README.md)
называет structured output beta и допускает JSONDecodeError даже при parse.
Проверенный локальный langchain-gigachat действительно передаёт strict=True;
его документация называет это best-effort. Поэтому клиентская валидация
остаётся обязательной. Первичный протокол `6d7c2a6` и его хеш не переписываются;
новая схема фиксируется отдельным состоянием.

Плоский JSON Schema smoke также дал 0/4: семь полученных `stop`-ответов
синтаксически неверны, плюс одна ошибка соединения. Упрощение nullable
не устранило сбой. Следующий контроль на тех же четырёх train-единицах:
`--schema-style flat --output-method function_calling`, отдельный каталог
`feature-function-runs`. Меняется штатный способ structured output, без
изменения рубрики, полей, модели, T/top_p или клиентских исключений.
Метод включён в идентичность запроса; старые JSON-ошибки не подменяются.
Это вызов функции возврата данных, без выполнения внешних действий.

Первый запуск function calling остановился **локально до API**: создаваемая
исследовательским harness функция не имела обязательного описания. Адаптер
исправлен с использованием существующего `create_simple_output_model` ноды:
enum передаётся строками, после валидации восстанавливаются числовые признаки.
Это исправление нового harness, а не выявленный дефект исходного judge.
Отдельный тест проверяет реальный конвертер langchain-gigachat и модель
`gigachat.models.Function`; весь набор — 133 passed. Старые JSON Schema
состояния остаются доступными в истории Git и сырых артефактах.

Исправленный function calling smoke завершён: 4/4 валидных на тех же
train-единицах против 0/4 у обоих JSON Schema вариантов. Во всех четырёх
ответах признаки максимальны и итог равен 2; это успех формата, не качества.
Запущен полный ПОСТ: 150 train + 63 dev, включая сохранённый smoke;
калибраторы обучаются только после сбора всех ответов.

станут те же четыре train-единицы с исходной nullable JSON Schema, в каталоге

по умолчанию. Полный уже запущенный function calling продолжает использовать
